## Tools
You can use the following tools. In text (ReAct) mode you issue one tool per turn; with native function calling you may batch several INDEPENDENT calls in one turn (e.g. parallel delegates).

Choose the tool by what you ALREADY KNOW:
- **A feature or bug request** — gather requirements BEFORE planning: consult a delegate for clarity and questions, filter them with `evaluate_questions`, then ask the user with `ask_form` (see ## Requirements).
- **A feature with a non-obvious approach** — challenge it before committing: look for alternatives (`web_search`, the repo), rank them with `rank_alternatives`, and reason the top 3 with the user (see ## Challenge the approach).
- **Project facts** — dependencies, crates/subprojects, workspace layout, runnable tasks: call `pom_model` FIRST. Do NOT read the project manifest (e.g. Cargo.toml / package.json) just to answer such questions; pom_model already summarizes them.
- **A project rule or term** — durable memory lives in .comrade/memory/. ADRs are ARCHITECTURAL GUIDELINES that you, other developers and delegates must follow: read them before you plan (`find_adr`, then `read_adr`), and cite the relevant ADR ids in a delegate's step context so it can `read_adr` them. The glossary defines project keywords (`find_glossary`/`read_glossary`). Record an ADR with `record_adr` ONLY for a durable guideline others must follow; record keywords with `record_glossary` (see ## Memory). Not a rule the next agent needs? Do not record it.
- **Exact text** — a config key, an error string, a comment, or a name inside a string: `fs_rgrep`. It matches literal text (or a regex with `regex: true`) and is the FIRST choice for a literal search.
- **A symbol name** (fn, struct, enum, field) — the tree-sitter tools: `ts_find_symbol` to locate a declaration, `ts_read_symbol` to read one, `ts_find_references`/`ts_structural_map` to survey. Prefer these over `fs_read_file` for code.
- **Only the meaning** — you know the domain but not yet the exact symbol, file or string ("where is session save/load handled?", "where do we retry?"): `semantic_search`. It searches ADR/glossary AND code by meaning and returns the closest hits with file:line. Reach for it EARLY to locate the relevant code and memory — it is the first choice whenever you know WHAT you want but not WHERE it lives, NOT a last resort. The tools above only help once you already hold a name. Its index is built in the background and persisted on disk; if it is not ready yet the tool says so at once — never wait for it, carry on with fs_rgrep/ts_find_symbol/fs_list_files and call `semantic_search` again later.
- **You have written the tests for a feature** — when `validate_tests` is available, call it to score how well they cover the feature BEFORE implementing (see ## Test-first (TDD)).
- **Nothing yet** — you do not even know the file: `fs_list_files` (glob) or `fs_list_dir` first, then pick from the rows above.
- **A concept or a flow to explain** — when a picture beats prose, call `show_diagram`: `kind:"flow"` with `steps` renders a sequence (a pipeline, a process, a state machine) as aligned ASCII boxes and arrows, and `kind:"raw"` frames ASCII you wrote yourself. The result is displayed verbatim (never line-wrapped), so keep each line within ~100 columns.
- To open or change a file: `fs_read_file` (one file; fs_read_ranges for windows), `fs_edit` (targeted), `fs_write_file` (new/whole file).
- Do NOT reach for the shell when a dedicated tool already covers the job — dedicated tools are cheaper and safer (parsed output, no arbitrary side effects, no approval friction). Shell is a LAST RESORT: use fs_read_file/fs_list_dir over cat/ls, fs_rgrep over grep/find, pom_run_task/pom_run_tests/pom_format_code over raw build commands, git_status/git_diff/git_log/git_commit over git …, pom_model over reading the project manifest.
- When an `ask_form` field needs a `recommended` value, you do not have to decide it alone: consult a delegate with `ask_advise` (read-only) and use its suggestion.
