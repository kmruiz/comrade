# 0097 - Images ride the one user message as OpenAI content parts, gated by [llm].vision
status: accepted
date: 2026-09-28
tags: images, multimodal, tui, llm, config
summary: A user message carries its text and images together as OpenAI content parts on the ONE message; images come from a path in the prompt or the clipboard, the media type is sniffed from magic bytes, and whether they are sent at all is decided by `[llm].vision` (auto/on/off) with a textual placeholder and a notice when the model cannot see.

## Context
The user asked for image support: the model can read an image from the worktree, or one dropped into the terminal or pasted, and a pasted image may be accompanied by text. `ChatMessage` (crates/comrade-core/src/llm.rs) had a `content: String` and user prompts were a bare `String` all the way from the TUI to `run_agent_with_history`; the `Tool` trait returns only a `String`; nothing anywhere knew about images or model capabilities.

## Decision
One user message carries the text AND its images; the images are OpenAI-style content parts (`{"type":"image_url","image_url":{"url":"data:image/png;base64,…"}}`) on that same message. Concretely: (1) `comrade-tool::UserInput { text, images: Vec<ImagePart> }` is the message type everywhere (TUI submit/steer, `run_agent*`, `Steer` channel, `AgentEvent::User`, `ContextManager::push_user_input`); `ImagePart { name, mime, base64 }` lives in comrade-tool/src/attach.rs. (2) The media type comes from MAGIC BYTES (`ImageMime::sniff`), never the extension; PNG/JPEG/GIF/WebP; at most `MAX_IMAGES` (5) per message, at most `MAX_IMAGE_BYTES` (8 MiB) each — an oversized image is REFUSED with a notice, never shrunk or silently dropped. (3) `ChatMessage` keeps `content: String` + `images: Vec<ImagePart>` and converts to/from a private `WireMessage` (`#[serde(from, into)]`), so `content` stays a plain JSON string whenever there are no images — byte-identical to before, which prompt caching and every plain provider rely on. The display name is deliberately NOT on the wire. (4) Image sources: any image path in the submitted prompt text (typed, dropped or pasted by the terminal; quoted or `\ `-escaped, `file://`, absolute or relative to the project root) plus the system clipboard (`arboard::get_image` → RGBA → PNG via the `png` crate) on C-y / Ctrl-V, held as `pending_images` until the next message. (5) Support is decided by `[llm].vision = "auto" | "on" | "off"` (default `auto` = a model-name heuristic, `LlmCfg::supports_vision`). When the model cannot see, the run continues: `UserInput::downgrade_images` replaces each image with `[image not sent: … - name]` in the text and the agent emits an `AgentEvent::Notice` naming `[llm] vision`. (6) `ContextManager::total_tokens` charges a FLAT `IMAGE_TOKENS` (1100) per image, never the base64 length. (7) Delegates never receive images: `drain_steer` is called with `vision: false` from the delegate sub-loop, downgrading an image steer to the text placeholder in the usual harness note.

## Rationale
Content parts are the format every OpenAI-compatible endpoint (and Anthropic through its shim) actually accepts, and keeping them on the SAME message preserves the prompt's meaning and the role alternation the context manager already protects. Magic bytes make a mislabelled file still correct. A private wire type keeps the no-image JSON byte-identical, so nothing that depended on the old shape (prompt caching, the serde round-trip test, ReAct mode) changes. Gating on `[llm].vision` with an `auto` default means the feature is on where it can work and honest where it cannot, and the placeholder + notice keeps a run from dying on a capability the user did not know about.

## Alternatives considered
(a) A model-callable tool (`fs_read_image`) returning the image in its tool result — rejected: the `Tool` trait returns only a `String` (comrade-tool/src/tool.rs), so this would change the trait and all 12 tool crates, and a tool result is a poor home for an image. (b) Send the image as a SECOND message after the text — rejected: it splits one prompt into two turns, breaks role alternation rules the context manager already fights (ADR 0059) and doubles the request. (c) Send raw pixels as a custom field — rejected: no provider understands it. (d) Always send images and let the provider fail — rejected: a text-only model then errors out the whole run. (e) Rely on the file extension to decide the media type — rejected: a mislabelled `chart.png` that is really a JPEG would be sent with the wrong type.

## Scope
Every path a human prompt takes into the main agent: the TUI prompt bar (submit, ctrl-Enter queue, mid-run steer) and the image attachments themselves. Deliberately NOT covered: a model-callable image tool, images in tool results or in the system prompt, resizing/re-encoding a large image, image OCR, images for delegate sub-agents, and re-loading attachments from a saved session file.

## Impact
A vision model works with no config change; a text-only model is never sent an image it would fail on, and the human is told what was left out. `run_agent`/`run_agent_with_history`/`run_headless` take `impl Into<UserInput>`, so a plain `String` still works at every existing call site. Adding a new image source means producing an `ImagePart` and putting it in `UserInput.images` — do not add a parallel field or a second message. A new provider or media type is one arm in `ImageMime` plus one in `ImagePart::from_data_uri`. Known limits: the clipboard path needs a running X11/Wayland clipboard (arboard) and always names the image `clipboard.png`; images are not re-read from a saved session file (the name is not on the wire); attachment paths resolve against the App's project root, not the session worktree.
