## Context
New occurrence of the recurring TUI freeze (#24/#25/#28), this time with the model-server side fully captured. logs.txt is a paste of the LM Studio (localhost:1234, mistralai/ministral-3-3b, ctx 60160, 4 parallel slots) developer-log page for the frozen run. User report: "app froze; the local model kept working until it finished; because the app was frozen it didn't receive any other requests."

## Decision
What the log proves (verified by parsing logs.txt): (1) 50 sequential /v1/chat/completions requests from ONE Comrade agent run, 00:27:15 -> 00:27:39; conversation grows 38 -> 137 messages (~19.2k slot tokens at the final slot release, well under ctx 60160 -> NOT a context overflow). (2) Every one of the 50 requests completed server-side ("Finished streaming response" + slot release logged for each); the LAST completed at 00:27:39 and then ZERO further requests. No [ERROR]/client-disconnect lines anywhere -> app did not abort; it wedged. Page saved ~00:29, ~90s of silence after the last completion. (3) Freeze is app-side, at/just after the final reply finished streaming - server finished the in-flight generation exactly as the user described. (4) finish_plan was NEVER invoked (it appears only once per request as the tool-schema definition, 50x total). The run's tail turns were thrash: repeated rgrep duplicate-call guardrail errors, update_plan "no step matched given index/text" errors (3x in the last block), read_ranges on a nonexistent crates/command/command.rs. (5) Cadence was ~0.5 s/turn (not a stall): LM Studio KV reuse made prompt eval shrink 297 ms/1341 tok -> 35 ms/94 tok; eval ~116-120 tok/s. So this freeze happened on a FAST local run, unlike the stalled-model cases #24/#28. Hypothesis consistent with everything: with the model streaming deltas ~120 tok/s into a cap-512 events channel (main.rs:172), the UI task wedges in redraw/on_agent_event under burst load (shape (a), #25 suspect iii/i: per-token redraw cost grows with the 137-message conversation; run task then blocks on tx.send at agent.rs:472 behind the full channel and the app looks dead; Esc can't help because the UI task is the one stuck). Next step if it recurs: capture `gdb -p <pid> -batch -ex 'thread apply all bt'` while frozen - expect UI thread in ratatui draw/layout and run task in events_tx.send.
