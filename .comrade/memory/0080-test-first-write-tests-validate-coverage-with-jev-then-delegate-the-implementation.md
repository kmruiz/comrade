# 0080 - Test-first: write the tests, validate coverage with Jev, then delegate the implementation
status: accepted
date: 2026-09-27
tags: tdd, tests, jev, typesafe, validation, delegation, prompts, tools, comrade-core
summary: The lead is guided to work test-first: write the tests for a feature, score how well they cover it with Jev (the new `validate_tests` tool, input `{ feature, tests }`, one score question over none/sparse/partial/good/comprehensive), and only on an ACCEPTED verdict (top two levels) delegate the implementation with the tests as the spec, then refactor; the prompt also demands the least code that passes, treats refactoring as essential, and picks test types by the pyramid (more unit than integration, more integration than functional). It is advisory, not a hard gate.

## Context
The human wants the team to practice TDD as much as possible: the tech lead writes the tests for a feature first, those tests are validated by Jev to see whether they cover the feature well enough, and only then is the implementation left to a delegate; after the tests are green the lead (or a delegate) refactors. The lead already plans and delegates, and Jev (TypeSafe) is already wired for the guardrail, so the missing pieces were (a) a coverage check and (b) prompting that pushes the test-first order. The human chose an ADVISORY mechanism (no hard gate), a single coverage score, acceptance at the top two of five levels, and left the refactor to the lead's judgement.

## Decision
1. Extract the Jev HTTP transport into a shared client, `crates/comrade-core/src/jev.rs` (`Jev::evaluate(state, questions) -> answers`, plus `noul`/`score`/`top_level` helpers, `Jev::from_cfg`). `JevGuardrail` is refactored onto it; the client is configured by the existing `[guardrails]` table.
2. Add the `validate_tests` tool (`crates/comrade-core/src/tdd.rs`), registered only when Jev is configured. Input `{ feature: string, tests: string[] }` (a lone string is also accepted). It sends `state = { feature, tests }` and one `score` question ("how well do these tests cover the feature's required behaviour?") over five levels `none / sparse / partial / good / comprehensive`, and returns an actionable verdict.
3. Acceptance is the top two levels: the weighted `score` must be `>= 3.0` of 4. The tool's result is DATA - one line `Test coverage X/4 (label): ACCEPTED|NOT ENOUGH (threshold 3.0/4)` - deliberately not an imperative, so it never reads as an instruction injected through tool output (## Trust boundaries). The ACTIONS live in the prompt section: ACCEPTED -> delegate the IMPLEMENTATION (the tests are the spec and must not be weakened, skipped or deleted) and refactor once green; NOT ENOUGH -> strengthen the tests and call again, do not implement yet.
4. Prompting: a `Test-first (TDD)` section (crates/comrade-core/prompts/tdd.md) is included in the system prompt only when `validate_tests` is advertised, and crates/comrade-core/prompts/working-style.md steps 4-5 point at it. The section states the order (tests first, validate, implement only when accepted, then refactor with the tests green), and adds two quality bars the human asked for: the implementation must be the LEAST code that makes the accepted tests pass and refactoring is ESSENTIAL, not optional; and the tests must be comprehensive (real behaviour, no vacuous assertions) with the type chosen by cost/coverage — unit (cheapest/least), integration (middle), functional (most expensive/most) — following the TEST PYRAMID (more unit than integration, more integration than functional, never inverted). The `validate_tests` score question's instructions also weigh that pyramid balance.
5. Advisory, not a gate: the tool never blocks `delegate`; it returns the verdict and the prompt makes the lead act on it. `validate_tests` is lead-only (absent from the delegate/advise registries).

## Rationale
A separate coverage check gives an objective, cheap signal (one Jev call) that the tests are worth writing before any implementation exists, and it turns the tests into the spec: the delegate must satisfy them rather than invent behaviour, and the verdict explicitly forbids weakening them. Keeping it advisory avoids the brittle feature-to-job mapping a hard gate would need, while the conditional prompt section keeps every lead on the test-first order whenever Jev is available. Extracting the Jev client shares the connection and config with the guardrail instead of duplicating the HTTP code.

## Alternatives considered
(a) Hard-gate the `delegate` tool on an accepted validation — REJECTED by the human: mapping a delegate job back to a "feature" is fuzzy and would block legitimate work. (b) Have `validate_tests` itself kick off the implementation on acceptance — REJECTED: the lead owns planning and delegation, and the tool must stay side-effect-free. (c) A `noul` "adequate coverage?" with a probability threshold — REJECTED: the human asked for a graded score and acceptance at the top two levels. (d) Report per-aspect gaps (happy path / edges / errors) with extra questions — DEFERRED: the human chose the single score; the verdict already names the cases to add. (e) Always include the TDD prompt section — REJECTED: without a Jev key the tool is absent, so the section would reference a tool the model cannot call.

## Scope
Covers the coverage check and how the lead is prompted to use it. Does NOT change the delegate loop, the guardrail/steering mechanism, or the plan format, and does not itself run tests or commit. `validate_tests` is a network call to Jev; with no key it is simply not registered and no TDD prompt section is added.

## Impact
New shared `Jev` client, new `validate_tests` tool, new `Test-first (TDD)` prompt section, and README documentation; the guardrail keeps its behaviour on the shared client. Tests: `crates/comrade-core/src/tdd.rs` (acceptance boundary at 3.0, level mapping, string-or-array input), the updated `crates/comrade-core/src/guardrails.rs` unit tests, and the existing prompt/section wiring. Follow-up if wanted: report per-aspect coverage, or record the accepted test set in the session so a later step can re-check it.
