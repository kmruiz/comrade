# 0090 - Every session works in its own worktree and merges back with a fold-then-fast-forward
status: accepted
date: 2026-09-27
tags: worktree, git, session, safety, tools, tui
summary: Every TUI session works in its own git worktree on branch comrade/session-<id> and publishes with the approval-gated git_merge_session tool, which merges the target into the session branch (aborting any conflict inside the worktree) and only then fast-forwards the repository, so the main branch is never left mid-merge.

## Context
The user asked that every session work in a worktree and merge back when verified, because several sessions (and their delegates) editing one checkout can break the repository. Delegate jobs already isolate at `<repo>/.comrade/worktrees/<numeric id>` (ADR 0072) and the lead merges them back by hand with `git apply --3way`. Sessions had no isolation at all: `App` builds each session's `ToolContext` from the single repository root.

## Decision
EVERY TUI session runs in its own git worktree on its own branch `comrade/session-<id>`, created by `comrade_core::worktree::Worktree::open_on_branch` at `<repo>/.comrade/worktrees/session-<id>` (cut from the branch the repository has checked out — auto-detected, so a repo on `master` works as well as one on `main`). The session's `ToolContext.project_root`/`cwd`, its `MemoryUndo` root and its system prompt's working directory are all that worktree, so the repository's own checkout is untouched while the session works. The session branches is `Worktree::current_branch` of the repo, read at merge time.\n\nPUBLISHING is the approval-gated `git_merge_session` tool (`crates/comrade-tool-git/src/merge.rs`), which the agent calls once its work is committed and verified. `Worktree::merge_branch_into_target` is a strict TWO-STEP operation and the order is the safety property: (1) fold the target branch INTO the session branch inside the isolated worktree — the only step that can conflict, and it is `git merge --abort`ed there, leaving the repository untouched; (2) `git merge --ff-only` the session branch in the repository, which cannot conflict because the target is now an ancestor. The repository is therefore NEVER left mid-merge. Uncommitted work is refused (\"commit with git_commit first\") and a branch with no commits beyond the target is a no-op.\n\nA LEFTOVER worktree or branch from a previous run is REUSED (`open_on_branch`), never destroyed: silently dropping it or falling back to the shared directory would lose unmerged work. Non-git projects, a detached HEAD and git failures fall back to sharing the repository directory.

## Rationale
The agent is the only party that knows when its work is verified, so it (not the UI) triggers the merge, through an approval-gated tool exactly like fs_edit/git_commit. Doing the conflicting merge inside the isolated worktree and leaving only a fast-forward for the repository is what makes \"several agents at once\" safe: no code path can leave the user's branch half-merged or dirty. Reusing leftovers rather than recreating them respects the rule that the harness must never silently discard a developer's unmerged work, which is also why a non-isolatable project degrades to the shared directory instead of failing.

## Alternatives considered
(a) Serialize writes with a global lock so only one agent mutates the repository — cheaper, but agents cannot work in parallel, which is the whole point; (b) one worktree for the whole TUI process shared by all its sessions — coarser, sessions still clobber each other; (c) a per-session staging branch switched in the single working directory — a switch mid-run moves files under the other agents' feet. Jev ranked the per-session worktree 1.00 vs 0.00 for the rest.

## Scope
Covers TUI session isolation, the merge tool and the merge algorithm. Does NOT cover delegate job worktrees (unchanged, ADR 0072), headless runs (un-isolated), pruning of leftovers, or the git status bar.

## Impact
A session's file edits, commits and memory writes land in its worktree and only reach the repository when the agent merges. Anything that assumed one shared checkout for sessions must now use the session's worktree path: `App::session_root` is the single source of truth, `Make_ctx_base` takes an explicit root, and `LiveState.worktree` must be swapped in `App::swap_live` alongside the other per-session fields. Safety rules that MUST hold: `git_merge_session` is in `DENIED_FOR_DELEGATES` (a delegate's worktree is nested inside the session's, so from there the \"main branch\" is the user's own checkout) and is absent from `READ_ONLY_TOOLS` (so an `ask_advise` advisor can never merge). Known follow-ups, deliberately out of scope: leftover session worktrees/branches are not pruned on exit (names are stable per session id, so they are bounded, and `open_on_branch` reuses them), and the git status bar still reports the repository rather than the active session's worktree. `session_bundle` gained a required `root` parameter; headless runs pass `deps.root` and stay un-isolated. Verified with `cargo test --workspace` (comrade-core 265, comrade-tui 203, 0 failures) plus `cargo clippy --all-targets`.
