# 0098 - Transcript images: collapsed cards opened with Tab, painted by ratatui-image into reserved chat rows
status: accepted
date: 2026-09-28
tags: tui, images, rendering, ratatui, dependencies
summary: Transcript images are collapsed `ImageCard` rows opened in place by Tab, painted with ratatui-image 9 (chafa off, half-blocks as the guaranteed fallback) into rows the row-cache layout reserves, with the terminal's graphics capability asked once, lazily, on the first open.

## Context
Images could be SENT (ADR 0097) but the transcript only showed a `[image: name]` text line, so the human could not see what the model saw, nor a chart the run produced. The chat is a row-cached scrolling text view (`ChatRowsCache` + `layout_chat_rows` -> `RenderRow` -> one `Paragraph`), which has no way to draw pixels, and the TUI already had an expand/collapse idiom for card bodies (`Msg::open`, `MsgToolCard.open`, `MsgFail.open`, toggled by Tab on the selected block).

## Decision
Images in the transcript are [ImageCard] messages (`MsgKind::Image`), COLLAPSED by default into one line ("🖼 name (size) — tab opens") and opened in place by the SAME key/idiom as a tool card: Tab on the selected block (also a mouse click, or M-x toggle-tool-card). Rules:
1. Rendering goes through `ratatui_image`, PINNED to 9.x (`ratatui ^0.29`; 10+ needs ratatui 0.30) with `default-features = false, features = ["crossterm"]` — chafa is off because its default feature links `libchafa.so` at runtime, which a distributed binary cannot rely on. Decoding comes from an `image` dependency limited to png/jpeg/gif/webp.
2. An OPENED card reserves its rows in the LAYOUT (`layout_chat_rows` emits blank `RenderRow`s tagged `image: Some(msg_idx)`), so scrolling, selection, the row cache and the mouse all keep working; `draw_chat` paints each visible run of those rows AFTER its `Paragraph` with `render_stateful_widget`. Never draw a picture outside the reserved span.
3. The row count comes from `crates/comrade-tui/src/images.rs` (`preview_rows` -> `image_cells`): fit the chat width keeping the aspect ratio, never ENLARGING past the image's own pixel size, capped at `MAX_PREVIEW_ROWS` (24), and ZERO rows below `MIN_PREVIEW_COLS` (40) — a preview squeezed into a few cells shows nothing.
4. The terminal's graphics capability is asked ONCE, LAZILY: the renderer starts on `Picker::halfblocks()` and the main loop calls `ImageRenderer::query()` (`Picker::from_query_stdio`) only at the first frame that shows an OPENED image, with the event thread gated off through an `AtomicBool` (`graphics_pause`) so the query's stdin reply cannot be swallowed by `event::read`. It blocks up to 2s, exactly once, and reports the protocol in the chat.
5. `ImageCard` holds `path: Option<PathBuf>` (PERSISTED, so a saved session can re-read its images) and `pixels: Option<Vec<u8>>` with `#[serde(skip)]` (a clipboard image is NOT persisted: embedding megabytes in a session file is worse than losing a preview). Never put an enum variant behind `#[serde(skip)]` for this — a skipped variant errors at serialization time and would break saving a session.
6. Pictures are cached per card NAME with the encoded `(cols, rows)` and a `stamp` (file size + mtime, or byte length), so a resize or a RE-PLOTTED chart is re-encoded while everything else is reused.
7. Discovery: `model_images` (shared with the submit path) scans the assistant's final answer, its reasoning and tool output for image paths, deduped across the session in `App.seen_images` and capped at `comrade_tool::MAX_IMAGES` per message. Clipboard attachments become cards at submit time from `ImagePart::decode()`.

## Rationale
Reserving rows in the existing layout keeps every behaviour the chat already has (scroll, fold, search, mouse, copy) working for free, whereas a graphics overlay would need its own geometry kept in step with the row cache. Reusing Tab matches what the human already does to open a tool card, so the new card needs no new muscle memory (the collapsed line names the key). Lazy querying turns a 2s startup tax into a one-off cost paid only by someone who opens an image, and gating the event thread is the only way to own stdin safely in a program whose event reader polls it on another thread.

## Alternatives considered
(a) Half-blocks only, hand-rolled as styled text spans — fits the row cache with no graphics layer and works everywhere, but can never show real pixels; rejected once the user asked for real pixels, and kept only as the FALLBACK protocol (`Picker::halfblocks`). (b) An overlay box over the chat (the existing dialog machinery) — simplest and most robust, but it covers the transcript instead of opening the picture in place; rejected by the user. (c) Bumping the workspace to ratatui 0.30 to take ratatui-image 11 — rejected: 10+ requires the newer ratatui and this TUI is 14k lines, so the upgrade is a separate, much larger change. (d) Querying the terminal at startup (the crate's documented pattern) — rejected because it can add up to 2s to EVERY launch (STDIN_READ_TIMEOUT_MILLIS = 2000) for a feature most runs never use. (e) Querying lazily from a spawned task — rejected: it would read stdin concurrently with the crossterm event thread, so the reply would be swallowed (or the query would time out) and both would see garbage.

## Scope
How the comrade TUI shows an image inside the chat transcript: the card, its layout reservation, the paint pass, the terminal capability query, the protocol cache and the discovery rules. Deliberately NOT covered: images in any other surface (the plan panel, dialogs, the M-x list), image WRITING/export, animated images (only the first frame of a GIF is shown), a full-quality viewer (the terminal preview is a preview; the line names the path so it can be opened elsewhere), and the model-callable image tool that ADR 0097 rejected.

## Impact
The human now sees the actual picture where terminal support allows it and a coarse half-block preview everywhere else. Consequences and limits: a terminal that answers the font-size query normally upgrades on the first open (kitty/iTerm2/sixel); one that does not costs up to 2s ONCE and falls back to half-blocks — never on every launch. Only the halfblocks path is covered by tests, because the graphics protocols need a real terminal: `crates/comrade-tui/src/images.rs` tests paint into a `TestBackend`, and the layout/paint wiring is covered by the app-level test `drawing_an_opened_image_card_paints_the_chat`. Adding a new image SOURCE means producing an `ImageCard` (file or pixels) and pushing `Msg::image(...)` — do not add a parallel render path. A future ratatui bump must also re-evaluate the ratatui-image pin.
