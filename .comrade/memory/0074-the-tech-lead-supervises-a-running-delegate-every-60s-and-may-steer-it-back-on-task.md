# 0074 - The tech lead supervises a running delegate every 60s and may steer it back on task
status: accepted
date: 2026-09-15
tags: delegate, supervision, small-model, context, config, prompts
summary: The tech lead now reviews a RUNNING delegate's transcript every `[agent].delegate_supervise_secs` (default 60s) through a new `UpwardAsk::supervise` one-shot out-of-band model call and injects any `STEER:` correction into the delegate's own conversation at the loop's rest point, at most 5 times per run; the overflow summary now also tells the delegate which dead-end work to discard.

## Context
A small delegate model (3B) loses focus mid-run: it re-reads what it already knows, repeats itself and lets its transcript grow until the provider kills the request with a context-size error, so the step fails after minutes of work. Today the parent only intervenes AFTER the fact - `recover_context` summarises a transcript that already overflowed (ADR 71, capped at 3 recoveries) - and `ask_upwards` (ADR 61) only helps if the delegate itself realises it is stuck. The human asked for the tech lead to intervene DURING the run: 'every 60 seconds, the parent agent will check what the delegate is doing and what it will do. The parent model will fix any problem on the plan and then send it back to the delegate. If the context is exceeded, the parent will analyse what has been done, remove any garbage work and steer the delegate again. Up to 5 times, as we have right now.'

## Decision
(1) New `UpwardAsk::supervise(&briefing) -> Result<Option<String>>` in crates/comrade-tool/src/ask.rs, defaulted to `Ok(None)` so every existing impl keeps compiling and a parent that cannot supervise leaves the sub-agent on its path. `None` means 'leave it alone'. (2) `ParentAsk::supervise` (crates/comrade-core/src/upward.rs) is ONE tool-less `chat()` to the session's own model with its own purpose-built prompt, bounded by `SUPERVISION_TIMEOUT` (90s) and parsed by the new pure `parse_supervision`: a first substantive line opening with `OK` -> `None`; `STEER: <text>` (also `STEER - x`, `STEER(x)`, markdown-bold) -> `Some(text)` with the following lines appended; anything else -> `None`. Fail open: a rambling answer is never taken as a correction. (3) `DelegateLimits::supervise: Duration` (default 60s), wired from the new `[agent].delegate_supervise_secs` (default 60, `0` = off) in crates/comrade-tui/src/main.rs for the `delegate` tool, and set to `Duration::ZERO` for `ask_advise` (an advice run is short and read-only: nothing to steer). (4) `MAX_DELEGATE_SUPERVISIONS = 5` per run. (5) The hook sits at the TOP of each `run_delegate_subagent` iteration, immediately after `drain_steer` and before compaction - the loop's rest point, where the history is between turns, so an injected correction cannot fall between an assistant tool call and its tool result. It fires only when the interval has elapsed, the cap is unspent, and a parent is actually wired; it re-arms the clock BEFORE calling (a review takes time), injects a returned correction with `push_user_merged(SUPERVISE_PREFIX + correction)`, and is wrapped in `invoke_within(idle_left(last_progress, idle_nudged), ..)` so a slow parent cannot eat the delegate's inactivity budget (ADR 68). It deliberately does NOT reset `last_progress`: supervising is the parent's work, not the delegate's progress. (6) The briefing is the delegated task (the first user turn) plus the tail of `compact::render_transcript`, capped at `SUPERVISION_TRANSCRIPT_CHARS` (8000 chars, cut on a UTF-8 boundary), and says plainly that the last assistant turn is what the delegate intends to do next. (7) On a context overflow the existing `recover_context` summariser prompt now also says: 'if it went down a wrong path, say plainly which part is a dead end that must be discarded or reverted, then give the corrected plan for exactly what remains' - which is how the parent 'removes garbage work'.

## Rationale
The parent must see the delegate's transcript to judge progress, and it must do so out-of-band, because the lead's own context is the resource delegation exists to protect - the same argument as the summariser in ADR 71, and the reason `supervise` mirrors `approve`/`summarise` (one bounded, tool-less chat; unusable answer = no change). Injecting at the loop's rest point reuses the two mechanisms already proven there (ADR 59's `push_user_merged`, which keeps the history API-valid, and the `drain_steer` rest point), so a correction cannot break the conversation and needs no new state machine. Bounding the call by the idle clock keeps the two budgets from fighting: a parent that stalls must not look like a delegate that stalled. The interval, not a per-iteration check, is what makes the cost predictable; the cap is what stops 'steer it again' from becoming an unbounded conversation with the lead.

## Alternatives considered
(1) Supervising from the main agent loop's turn boundary - impossible: the tech lead is blocked inside the `delegate` tool call for the whole run and never reaches a turn of its own while a delegate works. (2) Appending the delegate's transcript to the lead's own conversation and letting the lead steer from there - rejected for the same reason as ADR 71: it spends the lead's context to save the delegate's and pollutes its history with a sub-agent's chatter; `supervise` must be an out-of-band call. (3) A wall-clock timer thread that interrupts the loop - rejected: the loop must stay single-threaded and cancellable, and interrupting a delegate mid-tool would leave its history API-invalid; the interval is instead checked at the loop's existing rest points. (4) Reusing `ask_upwards` for the parent's correction - rejected: that is the delegate asking (capped by MAX_UPWARD_ASKS), sharing no trigger and polluting the escalation budget. (5) Removing the delegate's 'garbage' work from the parent side - rejected: the parent is a plain tool-less chat, so it has no fs access; it can only instruct the delegate, which does have the tools. (6) One shared budget for supervision and overflow recovery - not adopted (see Impact): the overflow cap of 3 is already covered by ADR 71's tests and semantics, and the two triggers fire on different evidence (a clock vs a provider error).

## Scope
The delegate sub-agent loop and the channel it uses: crates/comrade-tool/src/ask.rs (trait method), crates/comrade-core/src/upward.rs (`ParentAsk::supervise`, `parse_supervision`, `SUPERVISION_TIMEOUT`, and one sentence of the summarise prompt), crates/comrade-core/src/delegate.rs (`DelegateLimits::supervise`, `MAX_DELEGATE_SUPERVISIONS`, `SUPERVISE_PREFIX`, `SUPERVISION_TRANSCRIPT_CHARS`, `supervise_briefing`, `supervise_delegate`, the loop hook), crates/comrade-core/src/config.rs (+ tests), crates/comrade-tui/src/main.rs (wiring) and README.md. It does NOT change `enforce_budget`, the main agent loop, the overflow/`recover_context` MECHANISM (only its prompt), the idle/read/repeat/destructive guards, the ReAct parser, the ask_upwards budget, or how the tech lead re-delegates a failed step with `feedback`.

## Impact
A delegate that drifts off its step is now corrected within one supervision interval instead of being left to loop until the provider kills it, and an overflowed delegate is told which dead end to discard. Cost: at most 5 extra parent model calls per delegate run, each bounded at 90s and by the delegate's remaining idle budget; the parent's own context is untouched because the review is a standalone call. Trade-offs: (a) supervision and the overflow recovery keep SEPARATE caps (5 vs `MAX_DELEGATE_COMPACTIONS = 3`), so one pathological run can spend up to 8 parent calls - the human said 'up to 5 times', and folding both into one counter would change ADR 71's tested semantics; raise/lower either constant if a single budget is preferred. (b) the correction is not surfaced as a chat event, so the session shows only its effect - following ADR 61's precedent that escalations should be visible, surfacing it via the events API is a follow-up. (c) supervision applies to `delegate` and `delegate_parallel` jobs (both run `run_delegate_subagent`) - a job is supervised by the same session lead. Verification: 2 integration tests in crates/comrade-core/src/delegate/tests.rs - `a_running_delegate_is_steered_by_its_parent` (the correction reaches the delegate's NEXT request, exactly one review, and the briefing carries the task and the transcript) and `supervision_stops_after_five_steers` (a run spends exactly the cap) - plus `parse_supervision_is_a_correction_or_nothing` in upward.rs. Whole workspace green (cargo test --workspace). KNOWN LIMITATION: as in ADR 71, this feature could not be built BY a delegate - the configured 3B delegate corrupted Cargo.toml and config/tests.rs on the config step and mangled upward.rs on the next, so the code was written by the main agent; see ADR 65.


## Note
FOLDED, at the human's request (same day). The two caps documented above as separate (`MAX_DELEGATE_SUPERVISIONS = 5` for supervision rounds and the pre-existing `MAX_DELEGATE_COMPACTIONS = 3` for context-overflow recoveries) are now ONE shared pool: `const MAX_DELEGATE_INTERVENTIONS: usize = 5` in crates/comrade-core/src/delegate.rs. Both `recover_context` (proactive compaction and the reactive overflow hook) and the supervision hook test and increment the SAME `interventions` counter, so a supervision round can consume the capacity an overflow recovery would have used, and vice versa. Consequences: (a) the trade-off listed in Impact (a) - up to 8 parent calls in one pathological run - is GONE; one run now makes at most 5 parent calls of either kind; (b) `overflow_answer` no longer says "compacted N time(s)" but "this run has already spent its N parent interventions, so there was no budget left to summarise it again", because the count is no longer necessarily made of compactions; (c) both `MAX_DELEGATE_SUPERVISIONS` and `MAX_DELEGATE_COMPACTIONS` no longer exist. Rationale (retained): the cost the cap bounds is how many times the tech lead is dragged into ONE sub-agent's run, however it happens, and every round is a real parent model call either way; a run that keeps needing the lead is not finishing, and past the pool the lead re-delegates the step itself. Tests updated/added: `delegate_stops_intervening_after_five_parent_calls` (renamed from `delegate_stops_compacting_after_three_recoveries`; its script gained one overflow response, because after the fifth recovery an overflow now takes the fixed-footprint retry first and needs a further rejection to reach the partial answer) and the new `supervision_and_recovery_share_one_budget`, which drives a parent that ALWAYS steers and ALWAYS summarises against one shared counter and asserts it is asked exactly `MAX_DELEGATE_INTERVENTIONS` times in total before the run returns its partial answer - i.e. the shared pool is proven, not just documented.
