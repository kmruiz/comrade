# 0077 - semantic_search indexes only git-visible files, persists a readiness marker, and never blocks the agent
status: accepted
date: 2026-09-27
tags: semantic_search, indexing, performance, gitignore, persistence, async, tools, comrade-tool-memory
summary: The code index now takes its file set from git (tracked + untracked-but-not-ignored), so an ignored dependency tree is never indexed; each index writes a readiness marker on completion, and a search ranks only a finished index and otherwise answers "not ready" immediately instead of building synchronously.

## Context
`semantic_search` was reported as unusably slow on large checkouts; the concrete case is `~/Projects/useguild/chatapp`, a repo with ~268 real source files that also holds a gitignored `.venv` Python virtualenv with ~14,787 source-extension files (~475 MB). The code walker (`walk_code` in `crates/comrade-tool-memory/src/semantic/mod.rs`) hard-coded a skip list of only `.git`, `target`, `node_modules`, `vendor`, `.idea` and `.vscode`, so it walked, parsed and embedded the whole virtualenv. A cold build could not finish in a session, which also meant the "persistent, incremental" index never got built in the first place. Two more defects surfaced while fixing it: the binary store alone cannot distinguish "never built" from "built and empty", and `semantic_search::invoke` refreshed/build the index inside its own `spawn_blocking`, so a search on a cold or dirty project made the agent wait for the whole build.

## Decision
Three changes, all in `crates/comrade-tool-memory/src/semantic/mod.rs` and `crates/comrade-tool-memory/src/git.rs`:
1. The code file set comes from git when the project is a repository: `git::listed_files` = `git ls-files --cached --others --exclude-standard` (tracked files plus untracked files that are not ignored). A non-git project falls back to a walk that skips an expanded `SKIP_DIRS` (`.venv`, `venv`, `site-packages`, `__pycache__`, `.tox`, `.next`, `build`, `dist`, `Pods`, `.gradle`, …). Oversized files are rejected by stat size before being read.
2. Each index persists a small readiness marker (`<key>.status` for memory, `<key>-code.status` for code; `IndexStatus { model, docs }`) written when a build finishes. `load_if_ready(root, kind)` serves the resident index if present, else loads the persisted one when a marker for the current model exists, else reports "not ready". Markers are invalidated together with the index by `invalidate`/`rebuild`.
3. `semantic_search` never builds synchronously. `invoke` kicks the idempotent background `warm`, then `search_ready` ranks only the indexes that are ready; if none is, it returns immediately with a "not ready — do not wait, use fs_rgrep/ts_find_symbol and retry later" message. A partially ready search (e.g. memory ready, code building) returns its hits and notes the kind still building. `rebuild: true` invalidates the caches and returns at once while the rebuild runs in the background.

## Rationale
The dominant cost was never the embedding model, it was the input set: excluding the ignored virtualenv cut the candidate files from 15,037 to 268 (a 56x reduction) without touching the model. Git's own listing is the right source of truth for "the project" — it already encodes the project's `.gitignore` (and global excludes), it includes untracked-but-not-ignored files an agent just created, and it is cheaper than walking a huge tree. The readiness marker is the missing state that makes both persistence and asynchrony correct: it survives a process restart (so a previously indexed project serves instantly from disk) and it distinguishes a finished-but-empty index from one that has never been built. Making the search non-blocking is what turns a 153s cold build from an agent-stalling wait into a background job: the agent gets a truthful, immediate answer and keeps working with the keyword/symbol tools.

## Alternatives considered
(a) Extend the hard-coded skip list only (no git) — REJECTED as the primary mechanism: it cannot know every project's ignore rules and would still walk large non-ignored trees; kept only as the non-git fallback. (b) Add a `.gitignore` parser dependency — REJECTED: git is already a hard dependency (used by `dirty_files`/`head_sha`) and `ls-files` is exact. (c) Make the cold build faster by parallelising the ONNX session — REJECTED: measured previously (see the module docs) that multiple sessions are slower; the file set was the real problem. (d) Keep the synchronous search but bound it by a timeout — REJECTED: more complex and still makes the agent wait; the readiness gate is simpler and exact. (e) Store readiness inside the binary blob instead of a marker file — REJECTED: it would force parsing the whole (potentially large) index just to answer "are you ready?".

## Scope
Covers how `semantic_search` chooses code files, detects readiness, and schedules its build. Does NOT change the embedding model, the CSMV store format, the git-HEAD incremental refresh, the ranking (still exact dot product over a flat index), or the tool's read-only classification. The semantic_search rollup (#0022) still governs the feature's shape.

## Impact
Measured on chatapp: candidate files 15,037 -> 268; cold build 153s producing 328 memory docs + ~3,819 code chunks; incremental no-op 0.09-0.67s; code index 16.3 MB -> 6.8 MB. Steady-state searches are served from the resident index and background-refreshed. A first-ever search on a fresh large project now returns "not ready" for a while instead of blocking; the model-facing prompts (tools-intro.md, working-style.md, delegate-system.md) and the `semantic_search` ToolSpec description were updated to say so. Follow-up if cold builds still feel long on very large monorepos: an ANN structure and a content-addressed embedding cache remain deferred from the earlier index work.
