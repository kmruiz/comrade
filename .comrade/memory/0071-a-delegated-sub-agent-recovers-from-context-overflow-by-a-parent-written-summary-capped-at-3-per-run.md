# 0071 - A delegated sub-agent recovers from context overflow by a parent-written summary, capped at 3 per run
status: accepted
date: 2026-09-15
tags: delegate, context, compaction, small-model, prompts
summary: On a context overflow a delegate's transcript is summarised out-of-band by the parent model (UpwardAsk::summarise) and its history replaced with that summary so it continues; capped at 3 recoveries per run, after which the run returns its partial answer. The fixed-footprint overflow (prompt + tool schemas alone too big) is detected separately and must not spend a recovery.

## Context
Measured, twice. (1) In the 2026-09-16 prompt-audit session every delegated job failed server-side on its FIRST request with `llm error 400 Bad Request: {"code":500,"message":"Context size has been exceeded."}` - 8 attempts, no tool call ever ran. (2) ADR 6 records the same failure for ministral-3-3b, which is why the visual prompt-tightening had to be done by the main agent instead of a delegate. Diagnosing it exposed TWO distinct overflows that look identical to callers: (a) VARIABLE-history overflow, where what the delegate accumulated (reads, edits, tool chatter) no longer fits the window, and (b) FIXED-footprint overflow, where the system prompt plus the advertised tool schemas alone exceed it and nothing has been done yet. Only (a) can be fixed by summarising; a summary of an empty history still overflows. The user proposed: when a delegate's work exceeds its maximum content, the parent model summarises it so the delegate can continue, at most 3 times.

## Decision
(1) New `UpwardAsk::summarise(&transcript) -> Result<Option<String>>`, defaulted to `Ok(None)` so every existing impl keeps compiling and a parent that cannot summarise simply leaves the sub-agent on its previous path. `ParentAsk::summarise` makes ONE tool-less `chat()` to the session's own model with its own purpose-built prompt (which must restate the task, since the original user turn is what gets folded away), bounded by `SUMMARY_TIMEOUT` (120s) and validated by the pure `usable_summary` helper (fail open: a blank reply is not a summary). (2) The delegate loop recovers on BOTH triggers: PROACTIVELY when `ctxm.needs_auto_compaction()`, replacing the lossy `enforce_budget` at the exact point it would start degrading the history (armed once per over-budget episode, mirroring the main loop's `auto_compact_armed`, so a structurally over-budget history cannot summarise every iteration), and REACTIVELY when a model request fails with a context-overflow error, classified by `is_context_overflow` on the provider's own wording (deliberately no bare "too long" marker, which would catch the ReAct parser's legitimate `line too long` error). (3) Recovery reuses `compact::render_transcript` (now `pub(crate)`) and `ContextManager::compact`, so the delegate's summary and the main loop's compaction share one representation. (4) `MAX_DELEGATE_COMPACTIONS = 3` per run. When spent, the run returns `overflow_answer(...)` - its best-effort partial text plus a note that the transcript was compacted 3 times - rather than failing, so the parent can re-delegate narrowly. (5) The fixed-footprint case is gated out of the recovery budget by `history_is_material` (no assistant turn = nothing to summarise = it is the prompt and schemas that are too big). It is instead answered in native mode by ONE retry with a slimmer advertised schema set (`SLIM_SPEC_DROP`: web tools, read-only memory tools, ask_upwards, skill_*), and then by the same partial answer.

## Rationale
The user's design, with three corrections that only became visible once the two overflow cases were separated. (i) The parent must summarise OUT-OF-BAND: `summarise` is a standalone `chat()` whose transcript is data in a fresh request, never an addition to the tech lead's conversation - otherwise we spend the parent's context to save the delegate's, and the parent delegated precisely because its own context is precious. (ii) A reactive trigger is required, not optional: `enforce_budget` trims at a GUESSED `budget_tokens` (6000 by default), so when the real window is smaller the request still 400s - and that error is what actually killed the runs. 400 is absent from `is_retryable_status`, so it propagates straight to the loop and is catchable there. (iii) Exhausting the cap must not kill the run: `timeout_answer` already established "return the partial answer with a note" as this codebase's way of ending a truncated delegate, so `overflow_answer` mirrors it. Reusing `compact_history`'s primitives and the main loop's arming idiom keeps both compaction paths on one representation and one cost bound.

## Alternatives considered
(a) Summarise without a cap - rejected: each recovery is a real parent model call, and a delegate whose fixed prompt does not fit can never succeed, so it would loop until max_iterations. (b) Append the delegate's transcript to the tech lead's context and let the parent agent summarise it - rejected: spends the parent's budget to save the delegate's, and pollutes the parent's history with a sub-agent's chatter. (c) Fail the run once the cap is spent - rejected: discards everything the delegate did, when the parent can re-delegate narrowly with the partial result in hand. (d) Reuse `UpwardAsk::ask` for summarising - rejected: its system framing is "one of your sub-agents is stuck", which invites advice rather than a faithful briefing, and it shares the MAX_UPWARD_ASKS=3 escalation budget, conflating "help me decide" with "help me fit". (e) Summarise with the delegate's own model (`compact_history` with its client) - rejected as the default because a small model retyping its own work corrupts detail (ADR 65); it remains available through the trait's default. (f) Retry blindly with the same request - rejected: it is exactly what the harness did, burning all iterations on a 400.

## Scope
Covers the delegate sub-agent loop's context-overflow recovery and the channel it uses: crates/comrade-tool/src/ask.rs (trait method), crates/comrade-core/src/upward.rs (ParentAsk impl + prompts), crates/comrade-core/src/delegate.rs (classifier, predicates, cap, both hooks, slim retry, partial answer), crates/comrade-core/src/compact.rs (render_transcript visibility only). Does NOT change `enforce_budget` or the automatic trimming, the main agent loop's compaction, the idle/read/repeat/destructive guards, the ReAct protocol's parsing, the delegate tool-set curation in comrade-tui's delegate_registry, or the ask_upwards escalation budget.

## Impact
A delegate that outgrows its window now continues instead of dying with a provider error; the cost is at most 3 parent model calls per run, each bounded at 120s. A fixed-footprint overflow is now detected and can no longer silently consume all three recoveries, and in native mode it retries once with fewer advertised schemas. Verification: 2 unit tests (classifier wording incl. the negative `line too long` case; history_is_material) and 3 integration tests driving the real loop against a status-aware scripted server (recovers and continues; stops at exactly 3 and returns the partial answer; spends zero recoveries on a fixed-footprint overflow). Falsified by setting MAX_DELEGATE_COMPACTIONS to 0: the first two integration tests fail, the third still passes. KNOWN LIMITATION: in ReAct mode the tool listing lives in the system prompt, which the loop cannot rebuild, so a fixed-footprint overflow there goes straight to the partial answer without the slim retry. The summariser also cannot help when the parent model itself is the one that is too small. Note for the next session: this feature could not be delegated while it was being built - the configured delegate failed with the very overflow it fixes (it narrated a plan and called no tools across 2 attempts), so the implementation was done by the main agent.


## Note
Cap superseded (2026-09-16, ADR #74): `MAX_DELEGATE_COMPACTIONS = 3` no longer exists. Context-overflow recovery now spends from the SAME pool as delegate supervision - `MAX_DELEGATE_INTERVENTIONS = 5` per run in crates/comrade-core/src/delegate.rs - so a run gets 5 parent calls of either kind, not 3 recoveries plus 5 supervisions (which allowed 8). The MECHANISM described above is unchanged (proactive on `needs_auto_compaction`, reactive on a provider context-overflow error, out-of-band parent `summarise`, `history_is_material` gate, partial answer when the budget is gone); only the size and the sharing of the budget changed, and `overflow_answer`'s wording changed with it ("spent its N parent interventions" instead of "compacted N time(s)"). The three integration tests listed in this ADR's Impact still exist and still pass; the cap-3 one is now `delegate_stops_intervening_after_five_parent_calls`.
