# 0025 - Recurring "freeze after agent finishes plan" — capture recipe & suspects
status: accepted
tags: tui, freeze, plan, finish_plan, bugfix, diagnostics
summary: User: sometimes right after the agent calls finish_plan the whole TUI freezes (spinner stops, Esc/keys dead, needs Ctrl-C). Root cause NOT yet found; capture gdb backtrace of the frozen process before killing (per #24) and feed it back.

## Context
Reported against comrade-tui. Investigated the full path: finish_plan tool (comrade-tool-session lib.rs ~380-431) -> AgentSession::finish_plan (comrade-core/src/session.rs 219: marks all non-done steps Done, sets finished, emits AgentEvent::PlanFinished; all sync, short plan.write lock) -> TUI on_agent_event (tui.rs 1311: push_meta only). Run end is guaranteed: run_agent_with_history (agent.rs 372-405) always sends AgentEvent::RunEnd after run_agent_loop. TUI main loop (tui.rs 1840) is a tokio::select over kev/events/asks/dialog_ans/git channels + a 100ms spin tick gated on app.running; redraws every iteration with `let _ = terminal.draw(...)` (errors ignored). finish_plan tool is denied for delegates (delegate.rs denied_for_delegates) and is NOT approval-gated, so nothing blocks on it. Earlier, related freezes: #24 delegate sub-loop ignored CancellationToken (fixed, commit e0b8794), #21 delegate LoopTracker (fixed).

## Decision
1. When the freeze recurs, capture where the process is stuck BEFORE killing: `gdb -p <pid> -batch -ex 'thread apply all bt'` (Linux; macOS: `lldb -p <pid> -o 'bt all' -o detach -o quit`), plus `ps -o %cpu` to check for a 100% spin. Feed the backtrace to a fresh session. 2. Distinguish the two shapes: (a) main select task wedged in synchronous frame code (handle_event/on_agent_event/terminal.draw) — spinner freezes AND keys are dead; (b) only the run task stuck in an await (spinner still animates, Esc cancels) — that class was #21/#24. The report matches (a). 3. Suspects ranked while awaiting the bt: i) terminal.draw returning Err after the run's final frames and the error being ignored (`let _ =`), leaving a stale frame while the loop silently consumes keys (fits "Ctrl-C still quits": Ctrl-C is a key event handled before modals at tui.rs 1934); ii) a stale modal (pick/search/mx/dialog) eating keys after RunEnd; iii) content-dependent infinite loop in md_to_lines/layout (data-dependent, "sometimes"). 4. NOT the cause: finish_plan/session locks (sync and short), dialog reply channels (answer_top pops the dialog unconditionally, tui.rs 1414), events channel (drained every select iteration; RunEnd always sent).

## Consequences
No code change was committed: an intermittent whole-UI freeze must be fixed from a real backtrace, not a guess. A good cheap hardening once confirmed: surface terminal.draw errors instead of `let _ =`, and/or log modal state on idle keys. Full path map: finish_plan tool handler comrade-tool-session/src/lib.rs:431 calls ctx.session.finish_plan (session.rs:219) which emits PlanFinished; TUI handler tui.rs:1311.
